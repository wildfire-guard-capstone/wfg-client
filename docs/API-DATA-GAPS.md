# 화면별 데이터 공백과 [NULL] 표시

2026-11-11 사용자 결정: main의 UI·카테고리 이름·배치·지도 그리기를 유지하고, 연결할 수 없거나 제공되지 않는 정보는 **`[NULL]`**로 표시합니다. 화면 표시 문자열이며 HTTP 요청 본문에 문자열 `"[NULL]"`을 넣는다는 뜻이 아닙니다. 실제 nullable 필드는 명세의 JSON `null` 규칙을 따릅니다.

근거: [API v0.5 main c2ba98e](https://github.com/wildfire-guard-capstone/wfg-docs/blob/c2ba98eb67ce3a53bbe8d36006116e4e4113b76f/docs/%EC%84%A4%EA%B3%84/API-%EB%AA%85%EC%84%B8%EC%84%9C.md), 특히 포함·제외 범위, Incident·Weather·Proposal DTO, 6절 엔드포인트, 11절 우선순위. 확정 상태는 기존 PR #67·#68 및 노션 협의 기록을 함께 대조했습니다. main 커밋이 달라졌다는 이유만으로 노션의 확정 상태를 임의 변경하지 않습니다.

## 서로 다른 네 가지 이유

| 구분 | 문서 표기 | 뜻 |
| --- | --- | --- |
| A | 검토 중인 API 명세 대기 중 | 명세에는 있지만 개별 확정 근거를 아직 확인하지 못한 API. 노션 실제 속성은 `검토 초안`이며, 담당자가 지금 검토 중이라고 새로 확인한 것은 아님 |
| B | 현재 명세 미정의 / 범위 제외 | API나 필요한 필드 자체가 없음. 다른 미확정 API가 확정되기만 하면 자동으로 생기는 정보가 아님 |
| C | 확정 API와 기존 화면의 매핑 확인 대기 | API 자체는 확정. 기존 화면 분류와 응답의 뜻이 달라 대응 관계를 확인해야 함 |
| D | 응답 미제공 / 조회 실패 / 화면 미연결 | 명세 확정 여부와 별개로 실제 값이 null이거나 조회에 실패했거나 아직 화면 교체를 적용하지 않은 경우 |

**진화 7개·대피 7개 ↔ API 6개·6개의 차이는 C입니다. 검토 대기 API 12개 때문에 생긴 차이가 아닙니다.** PROP-01~05는 확정 범위입니다. 명세의 제안 항목 체계가 바뀌고 일부 내용을 합쳤기 때문에 UI의 14칸을 그대로 보존한 데이터 매핑이 필요합니다.

## 기존 제안 카드의 연결

카테고리명과 순서는 `src/data/scenario.ts` 원본을 그대로 사용합니다. API 응답의 항목명으로 UI 이름을 덮어쓰지 않습니다. 아래는 프론트 데이터 연결 기준이며 새로운 백엔드 명세 합의를 뜻하지 않습니다.

| S2 진화 우선지역·보호대상 선정 | S2 | 우선지역·보호대상 제안 연결. 시설 보호가 합쳐진 원문을 임의 분리하지 않음 |
| S3 진화자원 투입·배분·재배치 | S3 | 제공된 본문만 연결. 없는 개별 배치 좌표·추가 배분 계산을 생성하지 않음 |

| E3 취약시설·미대피 주민 조치 | E3 | 제공된 본문 연결 |

API E6는 응답 원본에 보존되지만, 대응 관계를 확정하기 전까지 기존 E7로 임의 배치하지 않습니다. 12개 응답 모두와 14개 화면 항목을 억지로 1:1 대응시키지 않습니다. 매핑하지 못한 카드도 기존 카드 구조 안에서 `[NULL]`로 보이며 발동 건수에 포함하지 않습니다. API가 `NOT_TRIGGERED`라고 명시한 항목은 기존 UI 규칙대로 발동 카드에서 제외합니다.

## 검토 대기 범위

명세에는 있으나 확정 근거 확인이 필요한 12개는 **USR-03~06, MAP-03~04, RES-03~05, BASE-02~04**입니다. 노션의 기존 `검토 초안` 속성은 그대로 두었습니다. 여기서 사용하는 ‘검토 중인 API 명세 대기 중’은 프론트 미연결 사유 안내이며 담당자의 진행 상태를 새로 판정한 것이 아닙니다.

반대로 **INC-02, PER-01, PER-02, PER-03은 명세에 있고 기존 협의 완료 범위**입니다. 노션에도 원래 상세 페이지가 있었습니다. 2026-11-11 확인에서 INC-02가 현장 보고로 분류되어 있던 것을 사진 기준 ‘산불 목록·현황’으로 옮겼으며, PER 3개는 ‘현장 보고(발화점·화선)’에 유지했습니다. 메인 페이지에 바로가기를 추가했고 중복 생성하지 않았습니다.

## 백엔드와 확인할 항목

1. UI S5·E5·E7과 API S2·E4·E6의 통합/대응 방식을 정할 것인지, 현재 `[NULL]`을 유지할 것인지.
2. 공식 발령 단계·접수 이력·대상 ID/좌표처럼 현재 제외된 데이터가 후속 범위에 들어오는지. 단순 미확정 API의 확정과 별개로 계약 변경이 필요함.
3. 계정 발급용 관할 ID를 어떤 방식으로 제공할지. 기관명으로 ID를 추정하지 않음.
4. 실서버 Base URL/접속 경로·CORS 또는 개발 프록시·테스트 계정. 이번 검증은 명세 모의 응답이며 실제 배포 서버 검증이 아님.

빈 배열을 정상 반환한 경우와 네트워크 오류를 구분합니다. 요청 오류·부분 실패는 `src/api/data-source.ts`의 `Remote`와 화면 브리지의 오류 기록으로 남기며, ‘데이터가 없음’을 ‘명세 미확정’으로 바꾸지 않습니다.
